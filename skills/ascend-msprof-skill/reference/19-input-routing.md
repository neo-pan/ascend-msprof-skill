# Route Source And Launch Inputs

Use this reference before new collection when the caller supplies source,
a runnable entry or an object. Reuse existing reports first through
[evidence navigation](12-evidence-navigation.md). If both source and reports
are supplied, inspect their binding and answer from usable evidence before
requesting another collection. A failed capture starts with the `collection`
question and its cited failure stage.

## Runnable Application Or Manifest

Read the supplied entry and [manifest contract](02-harness-guide.md): application,
implementation files, actual kernel selector and expected launch names/counts.
Confirm the build identity, input shapes/dtypes, correctness check and explicit
device binding. Follow calls into wrappers or shared libraries to identify the
launch path. A Python program can drive native ACL; a C++ program can invoke a
standard operator. Preserve relative companion files and required libraries.

Finish when the caller's entry, target and launch count are established, or
record the specific missing contract. Then choose a measurement below. Reuse
the provided harness when it represents the question; harness rendering belongs
to the caller/benchmark workflow, as described in [collection](03-collection.md).

## Ascend C Source

Read the kernel signature, host call and build configuration together. Distinguish:

- **Kernel fragment or kernel plus wrapper:** a `__global__ __aicore__` function
  and even a `<<<...>>>` call do not by themselves allocate inputs, select a
  device or provide a runnable test. Establish a matching caller-owned ACL
  harness, build options, complete ABI, buffers, tiling/control arguments and
  correctness check before live collection. Continue useful source inspection
  while the concrete missing launch/workload information is resolved.
- **Complete direct-launch application:** use its actual kernel and launch
  contract for ordinary app/op PMU. For instruction questions, prefer explicit
  simulator application mode with the same ABI and verified outputs.
- **Standard operator project:** inspect operator registration/build artifacts,
  shape/tiling dispatch and the actual caller. A standard build can carry
  parameter descriptions; successful TimelineDetail capture still requires a
  supported caller and usable metadata. C++ source alone certifies neither.

Finish by naming the build and launch path, not merely the source language.
If source was generated by TileLang, retain its generator/source identity even
when a native ACL harness launches it. This matters for reproduction and TD-001.

## TileLang Or Framework Source

Trace the Python entry to the actual kernel invocation. For TileLang/JIT input,
inspect retained generated Ascend C, the selected compiled library, build flags,
shape specialization, complete wrapper ABI and declared calls. Derive the name
from the generated entry rather than assuming `main_kernel`; distinguish a
Python function name from the device symbol and profiler's core suffix.

Ordinary app/op profiling can use a supported framework entry. For instruction
questions, check the calling-scope gate below before TimelineDetail. The tested
TileLang direct-launch entry lacks capture descriptions even with native ACL
allocation; [TD-001](18-timeline-detail-capture-defect.md) records that open defect.
When isolation is feasible, explicit simulation of the matching library through
a standalone ACL caller is the validated alternative for that workload.

Finish with the observed framework-to-kernel path and its capture prerequisites.
Unknown launch internals remain an evidence gap; a `.py` suffix or PyTorch import
is insufficient to select TimelineDetail. Avoid executing a training/inference
program solely to discover what source or a saved build receipt can establish.

## Compiled Object

Establish actual format and contents using [object evidence](16-object-evidence.md).
A host `.so`, an object container and a device ELF have different roles. Inspect
symbols, metadata and debug information without executing the object. Static
inspection can answer a static question with runtime binding left unverified.

For profiling, locate a matching application or supported operator config with
known inputs, target, full ABI and lifetimes. The
[9.1 operator guide](https://github.com/Ascend/msopprof/blob/56632dc4a944410c791538451dc2156a151bd105/docs/zh/user_guide/msopprof_user_guide.md#L81-L82)
distinguishes application mode from a JSON config describing a device `.o`.
The helper's `profile-pipeline` entry is application/manifest based; it does not
turn an arbitrary `.so` into a config. Simulator config mode has different SoC
selection and FFTS packing requirements; see [TD-001](18-timeline-detail-capture-defect.md#validated-workaround-and-its-limits).
Finish with static findings or a verified runnable binding, rather than guessing
arguments from symbol names.

## Choose The Measurement After The Entry

| Question | Route and gate |
|---|---|
| Device task time, utilization or bandwidth | Ordinary application/operator profiling through the matched entry. Follow [collection](03-collection.md) and check correctness, target and launch coverage. |
| Simulated instruction intervals, synchronization or source attribution | Explicit simulator application mode through a compatible entry; preserve injected libraries, verify numerical output and inspect actual trace intervals/selected lanes. Follow [pipeline evidence](14-pipeline-evidence.md). |
| Capture a supported framework operator's inputs for simulated instructions | Consider TimelineDetail only after establishing the documented calling scope, replay compatibility and parameter-capture prerequisites below. |
| Static symbols, metadata or PC mapping | Object inspection; retain the separate runtime-binding limit. |
| Existing Source hotspot/cache viewer products | Reuse retained products through the [viewer route](12-evidence-navigation.md#existing-viewer-inputs); source language does not add helper binary-decoding support. |

The [CANN 9.1 TimelineDetail definition](https://github.com/Ascend/msopprof/blob/56632dc4a944410c791538451dc2156a151bd105/docs/zh/user_guide/msopprof_user_guide.md#L86)
limits it to PyTorch third-party framework operators internally invoked through
single-operator APIs. It excludes second-level-pointer, Triton and
communication-fused operators, and application/range replay. Confirm the actual
calling path and input descriptions; supported scope alone does not prove
capture success. A previous TD-001 failure calls for metadata diagnosis rather
than an unchanged retry. Any alternative collection uses a separate run and
keeps the original failure recorded.

Explicit simulation is a separate
[documented application workflow](https://github.com/Ascend/msopprof/blob/56632dc4a944410c791538451dc2156a151bd105/docs/zh/user_guide/msopprof_simulator_user_guide.md#L320-L335).
`-g` supports source-line attribution, while unknown `:0` lines can remain.
Debug information does not supply argument sizes. Simulator intervals remain
separate from measured device latency and real-device overlap.

Complete routing with a short statement of the supplied material, actual entry,
selected measurement and any prerequisite still missing. Keep this in the
existing run notes/manifest workflow; no additional routing manifest is required.
For mixed or unfamiliar sources, follow the actual calls and available build
artifacts, retain unknowns and ask only for the missing information that blocks
the requested collection.
